# Store-Specific Shopping List Order — Proposal

## Overview

Two related, but separable, improvements to the shopping list, prompted by comparing the app's generated list against a handwritten list for an actual trip (see `comparisons/`):

1. **Store-specific category order** — the app's fixed category order doesn't match how any real store is laid out.
2. **Extra / ad-hoc items** — the handwritten list included things no recipe would ever produce (butter, tea, cookies, "Rachel's chocolates") — general household needs added by hand at write-time.

Either can be built independently; store order matters more once extras are blended in, since at that point the list is the single source of truth for the whole trip, not just recipe ingredients.

**Constraint: no hardware dependency.** The fridge-display hardware explored below (Raspberry Pi, pen-digitizer screen) is an optional enhancement for this household, not a requirement of either feature. Store profiles and extras must work the same for anyone printing to plain paper and adding extras from an ordinary phone browser — Print stays the default path, and nothing in the design should assume special hardware exists.

---

## Part 1: Store-Specific Category Order

Order the shopping list's category groups (Produce, Meat & Seafood, Dairy & Eggs, etc.) to match the walking order of a specific store location, instead of the fixed `CATEGORY_ORDER` used today. Households shop at more than one location — even two locations of the same chain can have different layouts (e.g. Lunds & Byerlys Golden Valley vs. St. Louis Park) — so this needs to support several saved orderings, not just one.

Auto-detecting a real store's aisle layout isn't feasible — there's no public API for it. Instead, let the household define their own named store profiles once (via drag-to-reorder) and reuse them on every shopping list.

---

## Data Model

New table: `store_profile`, linked to `household`. Category order is stored as an ordered list of the existing category names (the same 12 strings in `ShoppingListController.CATEGORY_ORDER`).

```sql
CREATE TABLE store_profile (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    household_id BIGINT NOT NULL REFERENCES household(id),
    name         VARCHAR(255) NOT NULL,     -- e.g. "L&B Golden Valley", "Cub - Plymouth Ave"
    sort_order   INT NOT NULL DEFAULT 0     -- position in the store picker dropdown
);

CREATE TABLE store_profile_category (
    store_profile_id BIGINT NOT NULL REFERENCES store_profile(id) ON DELETE CASCADE,
    category_name    VARCHAR(50) NOT NULL,
    position         INT NOT NULL,
    PRIMARY KEY (store_profile_id, category_name)
);
```

A household with no store profiles falls back to the existing hardcoded `CATEGORY_ORDER` — nothing changes for households that don't opt in.

## API

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/store-profiles` | List store profiles for the household |
| POST | `/api/store-profiles` | Create a new profile (name + category order) |
| PUT | `/api/store-profiles/{id}` | Rename or reorder categories |
| DELETE | `/api/store-profiles/{id}` | Remove a profile |
| GET | `/api/shopping-list?start=...&storeProfileId=...` | Existing endpoint, extended with optional profile param |

`ShoppingListController.buildCategories` already sorts on `CATEGORY_ORDER.indexOf(...)` at the end — swapping in a per-request ordered list from the chosen profile is a small, localized change.

---

## UI

### Managing store profiles
A "Manage Stores" option (e.g. a small link/gear icon in the Shopping List modal). Opens a modal listing saved profiles; each can be renamed, deleted, or edited. Editing a profile shows the 12 category names as a drag-to-reorder list (reuse a simple sortable list — no need for a new library if one's already in use elsewhere; otherwise a minimal HTML5 drag-and-drop list is enough for 12 items).

Creating a new profile: name it, then drag categories into shopping order. Defaults to the current `CATEGORY_ORDER` as a starting point so the user is just reshuffling, not building from scratch.

### Shopping list generation
A store picker (dropdown) at the top of `ShoppingListModal`, populated from saved profiles plus a "Default order" option. Remembers the last-used profile (e.g. in `localStorage`) so it doesn't need to be reselected every week. Selecting a store re-sorts the already-fetched categories client-side — no need to refetch from the backend, since the API already returns items grouped by category; only the display order changes. (Simpler than threading `storeProfileId` through the fetch — can be revisited if ingredient-level, not just category-level, ordering is wanted later.)

## Open Questions

| Question | Recommendation |
|----------|-----------------|
| Category-level or aisle-level granularity? | Category-level only for v1 — 12 groups is manageable to drag-reorder; per-ingredient aisle assignment is a much bigger project for marginal gain |
| Shared across household members or per-user? | Per-household, like pantry items — everyone shopping for the same house should see the same store options |
| What if he's at a store with no profile yet? | Falls back to "Default order" (today's `CATEGORY_ORDER`) |
| Sync order client-side or server-side? | Client-side re-sort of existing fetch result, per above |

## Part 2: Extra / Ad-Hoc Items

### Motivation

The generated shopping list only ever contains ingredients pulled from that week's recipes. Real trips also need general household restocking (butter, tea, cookies) that has nothing to do with the menu. Today those get written on paper alongside the app's list — the app should just absorb them.

### Behavior

A simple running list, scoped to the household (not to a specific week), so items can be added the moment someone thinks of them ("we're low on butter") from anywhere in the app, not just while looking at a shopping list. Items persist until checked off / removed — they aren't tied to a shopping-list generation the way recipe ingredients are.

When a shopping list is generated, extra items are merged in: run through the same categorization pipeline (Claude + keyword fallback) as recipe ingredients so "no salt butter" lands in Dairy & Eggs, "tortilla chips" in Canned & Dry Goods, etc., and sort into the same store-order categories from Part 1. Each item is tagged so it's visually distinguishable from recipe-derived ones (no `(recipe name)` suffix — just the item itself).

### Data Model

New table: `extra_shopping_item`, linked to `household`.

```sql
CREATE TABLE extra_shopping_item (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    household_id BIGINT NOT NULL REFERENCES household(id),
    description  VARCHAR(255) NOT NULL,
    created_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

No `checked`/`done` column — checked-off state today lives client-side only in `ShoppingListModal` (`checked` state, reset per fetch) and extras can follow the same pattern. Removing an item (checked off and cleared, or just deleted outright) is a `DELETE`.

### API

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/extra-items` | List current extra items for the household |
| POST | `/api/extra-items` | Add an item (`{ "description": "no salt butter" }`) |
| DELETE | `/api/extra-items/{id}` | Remove an item (checked off / bought, or added by mistake) |

`ShoppingListController`'s existing categorization endpoint pulls in `/api/extra-items` alongside recipe ingredients before running `categorizeWithClaude`, tagging each `IngItem` with `recipe = null` (or a sentinel) so the frontend knows not to render a recipe suffix.

### UI

- A lightweight "quick add" input — could live in the Shopping List modal header ("+ Add item") and/or somewhere always-reachable like the Planner tab, since the whole point is capturing things the moment you think of them, not just while shopping-list-focused.
- Items render inline within their categorized section, same as recipe items, just without the `(recipe)` tag.
- A way to clear items in bulk after a completed trip (reuse the existing "Uncheck all" footer pattern, but for extras: "Clear bought items").

### Workflow Notes

Two real moments this needs to hold up for, from how the household actually uses the printed list today:

- **Mid-week additions happen after printing.** The current paper workflow writes extras at the bottom of an already-printed sheet as the week goes. Once extras live in the app instead of on paper, the printed sheet goes stale the moment someone adds one on their phone — so **Print** needs to be re-runnable mid-week (not just once at menu-planning time) to pick up anything added since the original printout, without needing to regenerate the whole shopping list from scratch.
- **The pre-trip "anything else?" check.** Before heading to the store, someone always does a last pass — "anything more that needs to be added?" That's the moment right before leaving, not while planning the week. The quick-add UI needs to be fast to reach from a phone in that moment (not buried behind the full Planner flow), since it's answering that question on the spot, standing in the kitchen, right before walking out the door.

**Tradeoff — paper isn't being replaced, just supplemented.** The printed sheet's real value on the side of the fridge isn't that you can write on it — it's that it's physically anchored somewhere everyone glances at without opening an app. A phone can't sit there the same way. Rather than chase that (e.g. a fridge-mounted tablet), the practical split is: printed sheet stays the at-a-glance anchor, phone quick-add handles in-the-moment capture (which usually happens standing at the fridge/pantry anyway), and periodic reprinting reconciles the two. Not trying to make the digital version literally live on the fridge.

**Alternative — repurpose spare hardware instead of buying a tablet.** If there's already an unused Raspberry Pi around, the sunk-cost math changes: a small HDMI touchscreen (the official Raspberry Pi 7" touchscreen, ~800×480, ~$60–70, mounts flush to the Pi; or a larger 8–10" HDMI touch monitor for better readability across the kitchen) running Chromium in kiosk mode pointed at the shopping list page gives an always-on, auto-refreshing fridge display — closer to the paper anchor than a phone, without reprinting. Touch support means checking off items works the same way the paper list does. Mounting (magnetic or a slim bracket on the fridge door) and keeping it powered are the only real logistics; this is a "nice to have if the hardware's free" idea, not something to justify buying new hardware for.

To actually match the 8.5×11" footprint currently used, the small 7" display is too small — that's closer to a large phone. A **13.3" or 14" 1920×1080 HDMI touch monitor mounted in portrait** gets closest (~6.5×11.6" to ~6.9×12.2" visible area — narrower than paper since these are 16:9 panels, but similar height). These aren't Pi-specific accessories, just generic "13.3 inch HDMI touchscreen monitor" units (Elecrow, Uperfect, etc.). Driving one needs more graphics grunt than the tiny display, so a Pi 4 (not an older/weaker model) is the practical minimum, plus a USB touch controller if the monitor's touch input doesn't work cleanly over the HDMI+USB combo.

As of mid-2026, Raspberry Pi 4 pricing has been unusually volatile: the 1GB model is still $35, but a DRAM shortage (memory fabs prioritizing AI infrastructure) has pushed higher-RAM variants up sharply — a 4GB Pi 4 is now around $95, well above its historical ~$55. The 1GB model is probably underpowered for a Chromium kiosk driving a touch display, so budget closer to $95 for a new 4GB unit if the old Pi on hand isn't already a 2GB+ model.

**Handwriting capture, transcribed by Claude.** This is the version that actually delivers on "something we could write on" rather than just a display with a keyboard. It needs a step up from a plain touch monitor: generic capacitive touchscreens have no pressure sensitivity or palm rejection, so handwriting on them is unusable. A proper pen-digitizer display — sold as a drawing tablet-with-screen (Huion Kamvas, XP-Pen, etc.) — is what's actually needed.

Concrete pick: **Huion Kamvas 13 (Gen 3)** — 13.3", ~12mm thick, ~$239, 16384 pressure levels. Fits the size, thinness, and budget bar. It's pen-only (no finger multi-touch), but that's not a real loss here — the same pen used for writing also taps checkboxes, so nothing is lost by skipping the touch-enabled Pro variant, which runs closer to $400 for that capability alone.

Software side is straightforward given what's already planned for extras:
1. A canvas element captures pen strokes on the kiosk page (write directly on the fridge display, like the paper list).
2. On save, the canvas renders to an image and posts it to the backend.
3. The backend sends the image to Claude (vision) asking it to transcribe the handwritten item(s) into a list of strings.
4. Transcribed items feed into the same `/api/extra-items` flow already designed above — categorized, merged into the store-ordered shopping list, everything downstream unchanged.

This closes the gap between "digital" and "write on it": the ink itself is disposable (not stored as an image after transcription), but the *experience* is the same as writing on the fridge sheet, just captured into structured data instead of pen on paper.
