# Pantry / "What We Have On Hand" Feature Proposal

## Overview

Allow households to maintain a pantry inventory — a list of ingredients currently on hand — and automatically compare it against the shopping list to avoid buying things already in the fridge or cupboard.

---

## Data Model

New table: `pantry_item`, linked to `household`. Reuses the existing `Ingredient` entity pattern.

```sql
CREATE TABLE pantry_item (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name       VARCHAR(255) NOT NULL,
    household_id BIGINT NOT NULL REFERENCES household(id)
);
```

No quantity field to start — the goal is "do we have this ingredient at all?" rather than precise inventory management. Can be added later.

---

## API

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/pantry` | Return all pantry items for the household |
| PUT | `/api/pantry` | Replace the full pantry list (same pattern as meal ingredients) |

---

## UI

### Pantry management
A new "Pantry" button somewhere accessible (e.g., next to the Shopping List button in the Planner tab, or a dedicated tab). Opens a modal with the same `IngredientRows` component already used in the recipe and meal ingredient editors — autocomplete from the ingredient database, add/remove rows, save on close.

### Shopping list integration
When generating the shopping list, items covered by a pantry ingredient are visually distinguished — **grayed out with a "have it" label** rather than hidden, so the user can still verify quantities themselves (e.g., pantry has "garlic" but the recipe needs 8 cloves).

Example:

```
[Produce]
  ✓ garlic  (Asian Chicken Lettuce Wraps)           ← grayed, "have it"
  gala apples  (Copycat Wendy's Salad)
  green apples  (Copycat Wendy's Salad)
  onion  (Oriental Pepper Steak)
```

## Matching Strategy

Recipe ingredients are messy (`"½ Tablespoon minced garlic"`); pantry items are simple (`"garlic"`). Exact string matching won't work. Three approaches in order of complexity:

### Option 1 — Normalize + substring (start here)
Reuse the existing sort-key normalization (strip quantities, units, prep adjectives, comma/paren clauses) on both sides, then check if any pantry item is a substring of the normalized ingredient.

- `"garlic"` matches `"½ Tablespoon minced garlic"`, `"garlic cloves"`, `"garlic powder"`
- Fast, free, no extra API call
- Misses synonyms: `"green onion"` won't match `"scallion"`

### Option 2 — Claude match
After building the shopping list, send both lists to Claude Haiku and ask it to flag which shopping items are covered by pantry items. Handles synonyms and edge cases. One extra API call per shopping list generation (~$0.001).

### Option 3 — Hybrid (recommended)
Run normalize + substring first. For any remaining unmatched items, optionally run a Claude pass. Best of both — cheap for obvious matches, smart for edge cases.

## UX Decisions

| Question | Recommendation |
|----------|----------------|
| Hide matched items or show grayed? | **Show grayed** — quantities differ; user should verify |
| Where does pantry live? | Button near Shopping List in Planner tab |
| How often does user update pantry? | Ad hoc — no expiry/freshness tracking to start |
| Can pantry items have quantities? | Not in v1; add later if needed |
| Does clearing the shopping list affect pantry? | No — pantry is independent |

---

## Implementation Order

1. Liquibase migration — `pantry_item` table
2. `PantryItem` entity + `PantryRepository`
3. `PantryController` — GET and PUT endpoints
4. `PantryModal.jsx` — `IngredientRows` UI, load/save
5. Button to open pantry modal in Planner tab
6. Shopping list matching — normalize + substring in `ShoppingListController`
7. Frontend — gray out / badge matched items in `ShoppingListModal`
8. (Optional) Claude fallback for synonym matching
